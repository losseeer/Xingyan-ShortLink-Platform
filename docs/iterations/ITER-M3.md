| **演练脚本自己选错了量**（都是跑一遍才暴露的）：① 回源断言挂在热码上，`route_lookup{level="db"}` 量到 **0→0**；② 聚合表读回验证比行数，清单 387 / 读回 **384**；③ 一次性 MySQL 的"就绪"判据用 `ready for connections` 计数，结果 dump 灌进了 entrypoint 的**临时 initdb 服务器**，16 张表全读成 0；④ `VQ` 少写 `-e`，整条 SQL 被 mysql 客户端当成**数据库名**（`Unknown database 'SELECT 1'`），症状长得像"服务器连不上" | ① 热码被 Caffeine 全接住，压根不去碰 Redis 与 DB——"回源"只有冷码才走到，所以断言必须挂在一次都没被请求过的码上；② `SummingMergeTree` 合并折叠同键行、指标相加，行数天生不稳定（明细表是 Replacing，重复行合并时也会掉），所以"备份读回"要按引擎各选不变量；③④ 是对容器生命周期与客户端参数形状的想当然 | ①→R 段现在建一条冷码专门探测，并把"热码 0→0"这条反例留在注释与 §3；②→聚合表改比 `sum(pv)/sum(bot_pv)/sum(wx_pv)/sum(douyin_pv)/sum(browser_pv)/uniq(uv_state)` 六项、且影子表落地后立刻 `SYSTEM STOP MERGES`（否则一边合并一边数），明细表仍比行数但用备份前后两个计数构成**区间**；③→等 entrypoint 那行 `init process done` 再轮询 socket；④→`sh -c 'exec mysql -e "$1"' _ "$1"`。**存档里 B 行那句"落回备份计数区间"是措辞不准（聚合表比的是指标），脚本已改；不改已生成的存档本身（`bench/reports/` 只增不改）**——这条偏差就是它的勘误 |
| **演练的清理段只清掉了第一个 fixture 码，而脚本自己打印"已清 8 条码"**；同一坑也在 `accept-m3-02.sh` 的 Redis 清理里（只有第一个码的键被删）。另外新加的自检 **Z2 第一次跑就红**（明细残留 3 行），以及 **R5 的广播探测窗 30s 不够**（一次 60s 都没等到） | `docker compose exec -T` 会把**循环的 stdin 喝干**——`while read … < 文件` 里只要有一条 exec，第一行之后就被吞掉（复现极简单：三行文件的 while 循环里放一条 `compose exec -T redis PING`，只 echo 一次；给 exec 加 `</dev/null` 就三次都到）。Z2 红是 `ALTER TABLE … DELETE` 是**异步 mutation**，发完立刻数必然还看得到。R5 是前面那条"订阅恢复 12–18s"被我当成了判据：本机连续两次快速停起 Redis 后 30s 内没回来，而 R6 仍然 0ms 收敛——**闸门太窄只会把"还没等到"伪装成"坏了"** | 清理循环改成 `for c in $(tr -d '\r' < 文件)`（不吃 stdin），`accept-m3-02.sh` 那一行同样改法并留注释互指；Z2 加"最多等 60s 让 mutation 物化"的轮询并**同时打印明细与 link_route 两个残留数**（只有数字才能看出是清慢了还是清错）；R5 探测窗放宽到 60s 并把真实秒数记进存档，DESIGN 8.4 那句"量过两次 12–18s"改成"量过五次、离散度大、这条时间是闸门不是判据"。**教训：清理与探测这类"收尾代码"也要有自己的断言**，否则它给出的"已清"是一句没有证据的话——本轮就是靠 Z2 才发现前面六次演练都留了残留。修完之后**全表重跑一次**，所以 `bench/reports/` 里有两份：1438（第一次全表跑，六行数字有效、清理段有 bug）与 **1501（提交的那版脚本跑出来的，36/36，文档引用的就是它）**——按只增不改两份都留着，不删前者。顺带一条同族的小 bug：`want` 那行写成 `${SUB_SECS:-}>60s`，取到值时会打成 `12>60s`（1501 存档的原始计数里就有这一行），已改成 `${SUB_SECS:-超时}s`——显示类缺陷也照实留着不改存档，因为它不影响任何被引用的数字。改完之后又整表跑了一遍（本想只跑空段，`${DRILL_SECTIONS:-…}` 对空串也取默认值，等于全跑）：**仍是 36/36、Z2 残留 0 行**，所以这一串数字是可复现的，不是碰巧一次 |

## 5. 本期决策记录

- **M3 从"补一个字段"开始，而不是从看板开始**：看板要展示的转化率、对账脚本要算的差异率，都依赖"点击 ↔ 订单"能被同一个键连起来。缺这个键时先做看板，等于给一个空列画图表。
- **只加一列 `click_id`，不加 `trace_id`**：订单回传带的就是 `xy_click_id`（DESIGN 附录 B 已定），它是唯一有对外语义的对账键；`trace_id` 是内部日志贯通用的，落库了对账也用不上，多一列就多一份要维护的口径。
- **不加跳数索引**（用 §3 那组数字判的，而不是"感觉会慢"）：点查 0.3–0.5s、批量 `IN` 1000 个 0.8s，对账是离线批处理，这个量级完全够；换成加索引要为 4.33 GiB 历史 parts 重写一遍。要复现：`clickhouse-client --time --query "SELECT count() FROM xsl.click_event WHERE click_id='…'"`，读量看 HTTP 头 `X-ClickHouse-Summary`。
- **被频控拦下的点击写空串而不是造一个 id**：那一击压根没生成跳转目标，编一个 id 会让对账以为它到过落地页。代价是"历史行"与"被拦击"共用空串，区分方式（看 `risk_score=25`）写进 DESIGN 4.2 与 `accept-m2-13` 的 E2 断言。
- **发布顺序写进 DDL 注释**：先加列（幂等 `ALTER`）→ 再换 consumer → 最后换 jump。反过来会有一个"新 jump 已经在发 `click_id`、列还不存在"的窗口，而 ClickHouse 的 `JSONEachRow` 对未知字段默认直接报错，那段时间的事件会写不进去。
- **历史行不回填**：那个值从来没进过消息体，回填等于造数据。
- **M3-02：不另造"紧急封禁的 version 强校验通道"**。DESIGN 8.4 原来那句"紧急封禁走 version 强校验通道立即失效"读起来像要再开一条链路；落地时的结论是它就该是同两条条件写（表侧 `WHERE version<?` + 缓存侧 Lua 比较），广播只负责把它从 30s 压到亚秒。再建一条通道只会多一个没人验证的入口。
- **补行必须成对**（`link_route` + `code_tenant_index`）：创建时那次失败是整段没跑完，只补路由会得到一条"跳转能 302、管理面按码查归属却 404"的链接——比缺行更难解释。归属索引的 `tenant_id` 从事件的 `tenant_id` 拿，不需要回查主表。
- **状态机到上限就置 `2` 并停止自动重试**：一条坏 payload 若永远留在待投递，每轮都会吃掉一点批次额度，把后面正常事件的收敛拖慢；置 2 是"要人看"的信号，配套 `xsl_outbox_backlog{status="2"}` 与年龄指标。
- **`/internal/**` 刻意不进 `/api/`**：可达性由拓扑保证（网关与 nginx 都只路由 `/api/**` 与数据面），所以不必为它再造一套凭据；它跑的是与定时任务同一份逻辑，而条件写保证多跑不错、跑不坏。DESIGN 7.2 那句"内部：运维触发"由此从命名约定变成事实。
- **`@EnableScheduling` 从 `AccessQuotaReconciler` 移到 `AdminApplication`**：调度是应用级能力。原先挂在某个任务类上，第二个 `@Scheduled`（outbox 补偿）出现后就变成"那个类一旦被删除，另一个任务静默停摆"——这类失败不报错，只是再也不跑。
- **Pub/Sub 不做持久化、不重试、不 ACK**：它是尽力而为的加速器。丢消息的后果是该实例最坏等一次 L1 TTL（30s）自愈，而正确性早已由条件写守住；为它加 ACK 机制等于把"缓存收敛"升级成需要被验证的分布式协议，收益抵不上复杂度。
- **batch 默认 500、上限 5000 是用 7,955 行历史积压定的**（不是"感觉 200 太少"）：`ORDER BY id ASC LIMIT n` 会把新事件压在队尾，首轮实测新行压根扫不到（§4 第三条）。要复现整批代价：`accept-m3-02.sh` H 段，1,000 行 2 轮 1.393s。

- **batch_id 用「窗口 + 内容 hash」而不是纯窗口标识**：同一分钟桶的数会因迟到而变全，纯窗口 id 会把"更全的那一版"当重复投递丢掉。内容寻址之后两件事同时成立——重投（内容没变）id 相同被幂等吸收，补投（内容变了）id 不同、按桶覆盖更新。E 段就是拿一条真的迟到事件把这个语义跑出来的。
- **接收端自己重算 checksum 与 batch_id，发送端给的两个串只用来比对**：外部系统的声明不当事实用。验收脚本里又独立算了第三遍（C 段），所以 Java 两端一旦漂离 DESIGN 7.3 的算法，红的是脚本而不是一个没人看的单测。
- **"要不要给聚合表加 `valid_pv` 列"由实测关闭，不预防性优化**：明细 `FINAL` 的 10 分钟窗口实测 5ms / 读 6,755 行（表内 4,836 万行）⇒ 不动 MV、不加列、不碰老卷迁移。留着的那个出口（数字不可接受就换）也让未来的改动能被同样的方式质疑。
- **不建 nonce 表、不建水位/游标**：`batch_id` 幂等已经把重复投递消化了，水位不加也能靠"回看 N 个已关闭分钟"重投；两份新状态都要备份、要清理、要有人在出事时读懂，收益是零。代价如实写进 6.3：**迟到超过回看窗口的点击不进回传**。
- **`skipped` 与 `rejected` 分成两个结果值**：seed 里 1002/1003 两个租户会长期存在，"本部署不推它"如果混进"对端拒收"，指标每轮都冒假信号，真拒收反而被淹。命名口径写进 8.5。
- **sl-mock 不挂 nginx 对外路由、不经网关、不共业务分片库**：它的身份是"外部平台"，挂上域名就等于把自己变成我们系统的一部分，也就失去"对侧会拒收坏批次"这个验证价值（M3-04 的对账要有真会说不的对方）。
- **`@EnableScheduling` 挂应用类**（M3-02 定的规矩本轮生效）：`ConsumerApplication` 上开调度，`AttributionPushService` 只做任务；`ClickHouseWriter` 新增的 `rows()`/`longOf()` 也放它自己的模块，不把 HTTP 细节漏进业务类。

- **M3-04：假订单接口不鉴权，是写下来的决定而不是漏掉**。这一跳两端都在 mock 侧（购票页后端 → 平台），只往 `xsl_mock.mock_order` 里落归因字段，摸不到业务库；我们系统真正的对外契约只有 7.3 的"归因回传"那一行（HMAC + 校验和 + 幂等一样不少）。现在给它套一层假签名，只会多出一个没人验证、还让人误以为已解决了的入口。理由同时写进 DESIGN 附录 B 与 controller 的类注释。
- **`order_id` 由调用方生成并当主键**：真实形态里订单号本来就是购票系统生成的，用它做幂等键最自然。不做幂等的话"点了没成功再点一次"会把订单数弄虚高，而 ② 的分母就是订单数——症状会是"转化率莫名偏低"，离真凶很远，所以把吸收做在离真凶最近的那一行（`ON DUPLICATE KEY UPDATE times_submitted = times_submitted + 1`），并用 `times_submitted` 让它可观测。
- **② 的窗口按订单自带的 `first_click_time` 切，不按 `create_time`**：前者与 `click_time`/`minute` 同属点击侧墙上时钟，后者是 mock 服务器的 UTC 时钟（差 8 小时）。这不是风格问题——用错就会把整批正确订单算成"找不到"，报出一个纯假造的 100% 缺失（§4 倒数第二条）。
- **负向样本单独占一批活动，不混进主组**：混在一起会同时污染两条判据的分母，红了也分不清是"传输坏了"还是"这把键不认"。分成两组之后，主组保持 `missing=0`、负向组专门证明"报出的缺失条数 == 注入条数"，两条各说各的事，这才是"对账工具真的在比对两个集合"的证据。
- **对账拆成核对工具 + 验收脚本，不合并**：`scripts/recon-attribution.sh` 是可反复跑、按阈值给退出码的**运维工具**（T+1 手工核对也是它，不给窗口就自己按明细推区间）；`scripts/accept-m3-04.sh` 负责铺数据、调它、断言"阈值达成 + 坏样本被完整抓出"。合并的代价是运维得跑一遍 fixture，而验收会继承工具的随机性——与"`bench/reports/` 只增不改"是同一条纪律。
- **不把静态购票页改成自动下单**：它的职责到"回显归因参数"为止（M2-34），加副作用会牵动 M2-35 那 87 条断言。"扮演购票方"由脚本从 302 的 `Location` 抓真实 `xy_click_id` 完成，链路一步没少，而且抓到的值还要与明细里落库的值**逐个相同**才算过。
- **`<2%` 达成不等于"传输无损"**：本轮 ① 的差异是 **0.00%**，因为两侧取的是同一批真点击、发送与接收两端都幂等；阈值是给**生产**留的余量（迟到、丢消息、部分失败都会让它非零），不是给 mock 闭环定的。这句留在文档里，免得后来的读者把 0.00% 读成"链路无损的证明"。

- **M3-08：看板只走 `/api/v1/stats/**`，浏览器里一个密钥都不放**。那把 `api_key` 本身就是 HMAC 的 secret，放进浏览器丢的是**写权限**（能签创建/改链接的请求）。也**不做"看板专用 token"**：进浏览器就还是明文，加它只会让人以为隔离已经做了。代价如实写进 DESIGN 7.2 与 9.1——只读聚合数字对任何能访问入口的人是开放的，租户号直接放在 URL 路径里（放请求头会被误读成"有隔离"）。真正的隔离等 9.4 的 key/secret 分离。
- **接口清单要在接上消费者之后再复核一遍**：口径里写的"四条"是从页面倒推的，可那时页面还不存在。做出来才发现双指标要的是**租户时间序列**，与渠道分布不是同一条 `GROUP BY` 轴——借渠道接口的结果是页面给出一个**假事实**（"这个窗口里没有点击"），而接口 200、单测全绿。第五条接口就是这么补的。
- **"页面绑定的字段必须真的在响应里"做成可重跑的形状契约**。这一层是"接口对但页面错"唯一的自动化网兜：完整可重跑需要 headless 浏览器（Playwright 那类，几百 MB 起步），**本轮刻意不引入**——一个只有三页的只读看板不值这份依赖。代价照实写：页面渲染值与接口值的人工核对本轮由浏览器实测做一次并记进 §3，自动化只兜字段形状。
- **看板不是新容器**：nginx 静态托管 `sl-console-web/dist` + 在 **8081** 上做同源反代。80 端口上 `xy*.test` 的 `/` 已经被数据面的裸短码占了，看板抢不到前缀，同 `server_name` 换个端口是最省事的隔离办法。同源之后浏览器不需要 CORS，也不需要在 nginx 之外再多一个进程。`dist/` 不入库、`make up` 检查它在不在（挂空目录的症状是"所有路径 404"，长得像前端坏了）。
- **窗口上限 8 天是实测压出来的，不是拍的**（本项目第四次"由数字决定"）：24h/7d 每条 7–35ms，30d 每条 3.0–4.5s。面对这个数有两条路——给聚合表加 `blocked_pv` 重建 MV，或者把窗口收口。选了后者：看板答的是"最近投放得怎么样"，长窗口本来就有 `recon-attribution.sh` 那条离线路。加列重建 MV 被留在"要放开时才做"的位置上。
- **被频控拦下那一档必须被真实测到**：本轮之前所有实测里 `blocked_pv` 都是 0（数据里就没有超频的点击），于是"漏斗第三档存在"这件事一直只是代码上的事实。验收脚本特意建了一条 `rate_limit_per_minute=5` 的链接点 8 次，让 `blocked_pv=3` 真的出现在接口返回里。
- **备份范围把明细表也带上，不缩到"只备份聚合表"**：`click_event` 1.7 G、`make backup` 19s、`deploy/backup/` 一次一份（不入库、不自动清理，保留策略是运维动作）。取舍依据是这一格的承诺本身就是"数据丢失"——只备份派生聚合表的话，明细永远无法从别处重建，那句承诺就是空的。体积如实写在脚本输出里，跑前能看见。
- **读回验证一律不碰现有卷**：MySQL 用一次性容器（tmpfs + `--rm` + 不发布端口），ClickHouse 用 `RESTORE … AS xsl.*_vfy` 影子表且比完 DROP，另配一条 `live-untouched` 断言（现有明细表此刻只可能更多）。这是"恢复演练"在单机上破坏性最小且仍有意义的做法；真正的"覆盖式恢复"要停机、要备份回滚，属 P2 且个人项目不做。
- **`backups.allowed_path` 只给容器内一个目录，不给 `/`**：白名单存在的意义就是让一条 SQL 写不出宿主机任意路径。备份落点也刻意先落在容器卷里、再 `docker cp` 到 `deploy/backup/`——**"字节离开了数据库容器"这一步本身要被验证**，否则"备份"可能只是同卷内的一次复制。
- **演练断言的是行为，不是"容器停了"**：六行每行都在停机窗口里持续打流量，看成功率与错误码分布；恢复耗时全部记数（没有一个"很快"）；原始计数追加进 `bench/reports/`。顺序按影响面从小到大，Redis 停过之后**先探测两实例都能收到广播、再断依赖广播的项**（M3-02 那条教训的直接搬运，本轮实测订阅恢复 12s）。
- **只停中间件，不动 jump×2 的拓扑，也不给演练加新指标**：8.3 六行要验的是既有预案的行为。`DRILL_SECTIONS`/`DRILL_ARCHIVE` 两个环境变量是脚本自身的可操作性（单跑某几行、排练不写进只增不改的存档），不是产品开关。

## 6. 下期待办与风险

- **M3-01…M3-08 全部收口**（§2/§3/§5）：对账键、outbox 补偿、归因回传、端到端对账、看板五接口与三页。DESIGN 第十章那行 M3 出口标准的前**两条都已达成**；**剩下就是 §2 最后两行的 M3-09（8.3 降级演练全表）与 M3-10（多域名切换演练）**——它们对应出口标准的第三条"每条降级预案有一次实测记录"。M3 出口标准里那条"端到端归因对账误差 < 2%"第一次有了可点达的实测：**① 0.00% / ② 100.00%，注入的 3 条假 click_id 订单被完整报出，"只点击不回传"那批报的是 100.00% 而不是 `n/a`**（`accept-m3-04.sh` 78/78）。日常核对不必跑验收脚本，直接 `scripts/recon-attribution.sh <campaign_id>`（不给窗口就按明细自己推区间，阈值可用 `--max-diff`/`--min-join` 改，退出码可直接接告警）。**M3 剩下的两格运维演练也已交付**（M3-09 `drill-8-3.sh` 36/36、M3-10 `drill-domain-switch.sh` 13/13）——**DESIGN 第十章那行 M3 的三条出口标准全部达成，本期十格收口**。下面两条列的是演练时暴露出来、但不在 8.3 六行范围内的欠账（照实写在 §6 里，不当成已覆盖）。
- **看板页面数字的可重跑化（本轮刻意没做，附解除条件）**：`accept-m3-05.sh` 自动化的是"字段形状 + 接口与直查 0 容差"这一层；"渲染出来的文本 == 接口返回"本轮由真实浏览器人工核对一次（记在 §3）。自动化的代价是装 headless 浏览器（几百 MB 依赖 + 一个 Chromium），对一个三页只读看板不值。**解除条件**：看板开始出现**页面自己算出来的数**（占比、环比、前端聚合）——那时页面就是数据的加工者，只测接口不再够用。在此之前，风险由形状契约兜着（它已经抓住了"借错接口"这一类）。
- **看板的租户隔离本期不做（M3-05 定下的边界，不是遗漏）**：`/api/v1/stats/**` 不经网关 HMAC，浏览器里也不能放那把 key（key 本身就是 secret，放出去丢的是**写权限**），所以看板的聚合数字对任何能访问入口的人是开放的，租户号直接出现在 URL 路径里。这条已如实写进 DESIGN 9.1 风险表与 7.2。**解除条件**：DESIGN 9.4 欠着的 key/secret 分离与轮换落地（那时才有"只读凭据"可以给浏览器或服务端 BFF 用），或者真要给多个主办方分开看——两者任一成立才动它。刻意不加"看板专用 token"：进浏览器就还是明文，加它只会让人误以为隔离已经做了。
- **本机业务库里躺着 7,960 行压测残留**（`link_route` + `code_tenant_index` 各 7,960、对应 `short_link` 一行都不在、`outbox` 7,962）：绝大多数是 10-01～10-04 的压测批次留下的，见 §4 最后一条的分布。**这一轮没有清它**——清库是对用户数据卷的破坏性操作，而 M3-02 的 H 段实测（"重放整张 outbox 不会把路由表写回旧值"）正是拿这批积压做出的数字，清了等于把已有凭证的底座抽掉。**要清的话得先确认**：① 不再需要这批待投递事件做重放基准，② 或改成一份可重放的 fixture 脚本（`bench/` 里生成 + 清理成对）。顺带一条要修的语义：`OutboxSyncService.ensureTenantIndex` 只看"索引缺不缺"，不看"链接还在不在"，所以理论上会给已删除的链接补回归属索引（这 7,960 行里有多少是这么来的还没测；**解除条件**是看板/管理面要按 `code_tenant_index` 反查归属，那时"索引里有、主表里没有"就会变成可见的错误）。
- **M3-04 顺延三条（都附解除条件）**：① **0.00% 是 mock 闭环的性质，不是生产无损的证明**——发送与接收两端都在本机、时钟同源、幂等都在同一套代码里；**解除条件**是真接外部宣发平台（那时差异才会带上"迟到/丢消息/部分失败"这些真实成分，阈值也才第一次被真正考验）；② **归因口径没实现**——`first_click_time`/`last_click_time` 由调用方带回来、mock 只存不判，附录 B 说的"首触还是末触"目前等于"调用方给什么就是什么"，**解除条件**是看板要按归因口径出转化率（那时才需要平台侧的窗口规则与去重）；③ **订单只有归因那六个字段，没有金额/座位/场次**——端到端对账验的是"这笔订单能不能按 `click_id` 找回那次点击"，业务字段帮不上忙，**解除条件**是要出 GMV/ROI 类指标。
- **M3-03 顺延三条（都附解除条件，不是"以后再说"）**：① **一把 key 一个租户**——mock 侧 `XSL_MOCK_TENANT` 只认一个租户，多租户推送要等 key/secret 分离与轮换（DESIGN 9.4 欠着的那格）一起做，解除条件是真接外部平台或看板支持多主办方；② **迟到超过回看窗口**（默认 3 分钟）的点击不进回传，现在靠"只推已关闭分钟 + 回看"吸收，**解除条件**是外部平台要求可对账到个位数（那时才需要水位或平台侧发起重推）；③ `bot_pv` 恒 0、`valid_pv` 现在等于放行数——式子已经钉死，**解除条件**是 5.3 第 3 层评分规则表落地，届时数值自然变准、代码不动。
- **8.3 降级演练全表与多域名切换演练都已交付**（M3-09 `drill-8-3.sh` 36/36 + M3-10 `drill-domain-switch.sh` 13/13），M3 十格全部收口。演练时看板那条形态也确实被测到了：ClickHouse 不可达时五条 stats 全 **503**、错误信封是 `SL-5000` 而不是空数据（`StatsBackendException` 那条分支第一次有证据）。**但有两项"演练时要验的形态"本轮没进 8.3 六行，所以没做，别当成已覆盖**：① **Redis 停机期间发生的配置变更**，恢复后能否靠 outbox 条件写 + L1 TTL 收敛（本轮 R 段验的是"恢复之后"的广播与收敛，停机期间那次 PATCH 的 L2 写入失败路径要靠 `xsl_route_evict_total{result="error"}` 与同步器补写，目前只在异常路径出现、没被演练过）；② **宣发平台（对端）不可达时 consumer 要继续消费 Kafka**，只让 `xsl_push_total{result=error}` 抬头（M3-03 只验了"定时会跑"）。**解除条件**：①归入 M3-02 那条补偿链路，等"看板要显示收敛延迟"或真出现停机期间改配置的场景时补一段演练；②等真接外部宣发平台（那时对端不可达才有真实成分，本机 mock 停了也只是另一条 503）。
- **`deploy/backup/` 没有保留策略**（一次 1.7 G，跑几次就几个 G；本轮跑完只留最新一份，旧的手工删）。**解除条件**：真要按"每日 cron"跑就必须配套 `保留最近 N 份 + 落在第二块磁盘` 的清理动作——按本轮定的口径，调度与保留是运维的事，脚本只保证"能读回来"。
- **演练脚本会真实停机每行 10–40s，且 `docker kill` 那个容器不会自己回来**（见 §4 第一条）：中断这一轮会留下 stopped 的中间件。脚本有复位段（逐个 `start` 并等到 healthy + nginx 优雅 reload + 清 fixture），但复用前请确认 `docker ps` 是齐的，别把脏状态当成回归失败。
- **顺延两条（M3-02 明确没做，附解除条件）**：① `nextRouteVersion` 是"读当前 version 再 +1"的读-改-写，**两个 PATCH 并发打同一条码**时可能算出同一个 version（谁后写谁胜出、缓存按守卫只认先到那份）——单机单人操作不构成场景，**解除条件**是看板允许两人同时编辑一条链接，那时改成 `WHERE version=?` 乐观锁 + 重试；② `outbox` 的 `status=1` 行只做审计留存、**没有归档与保留期**，本机现在 8,955 行、扫描靠 `idx_status_create` 不受影响，**解除条件**是它涨到让"两库广播 count"变成可见成本（现在一次整批 ≈0.7s/500 行）。
- **看板三页顺延两格（都附解除条件，页面会显式标出来而不是悄悄少一列）**：① **转化那一档留空**——CH 里没有订单数据，而 6.4 定着"看板查询统一走 ClickHouse"，跨源现读会让转化率随两个源的延迟自己跳；**解除条件**是真接外部平台（届时转化数由回传侧对账链路给，见 M3-04 那条口径）或要做归因口径的首触/末次判定；② **管理面字段看不到**（`origin_url`/`status`/`expire_time`）——它们在 MySQL、接口要 HMAC；**解除条件**同上一条的 key/secret 分离，那时才谈得上给浏览器一条安全的读路径（或加一层服务端 BFF）。`device_type/os` 与 `click_id` 都已是真数据，所以渠道漏斗与"有效／被拦"两档不再是空列（这一部分本期就交付）。
- **风险三条**：① 活体测试与部署中的组件共用同一份数据（topic、outbox 表都碰到过），任何"新字段/新语义/新任务"的断言都要先对齐版本或走定点接口，否则拿到的是随机结果（§4 第一、三条）；② 本机宿主内存长期紧张（142 MiB 空闲、compressor ~7.3G），对外引用的性能数字仍要在安静宿主上复跑（ITER-M2 §6 那条口径继续有效）；③ **验收脚本会改部署状态**（`XSL_OUTBOX_SYNC`、`XSL_JUMP_MODE` 都动过容器），中断就留在脏状态——所以任何一轮红先怀疑环境，前置断言已经进脚本，但复用这些脚本时别绕开它。
